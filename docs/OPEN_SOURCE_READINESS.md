The final destination is the existing name `ichichuang/cinema-tv`, with `main` as the only ordinary branch and future official APK distribution in its GitHub Releases. This operation prepares a **source-only public launch with no production APK downloads**. Private visibility remains containment until the source gates pass and the owner authorizes the transition. Production migration and device gates remain separate; the signing incident is not closed by source publication. No permanent archive repository is part of this procedure.

## Recovery and same-name replacement

1. Preserve current refs and source in a verified Git bundle, the clean export and its mapping, exact CI results, private incident inventory, and required legacy APK hashes/metadata. Preserve the prior encrypted signing recovery archive. Never execute historical release workflows or restore caches into a signing environment.
2. Encrypt recovery evidence outside the candidate, restrict access and place a second copy in an owner-controlled offline fault domain. Keep recovery material separately. Actually decrypt into a new private staging directory, verify archive and bundle integrity, restore the intended ref, compare every required file/hash, and record the result. A same-machine archive is not an offline recovery check. No password/key values belong in the report.
3. Prefer deleting the contaminated repository and creating a new **Private** repository with exactly the same name, populated only from the verified local root. Prepare all export/build/recovery evidence first and obtain explicit confirmation immediately before repository deletion/recreation. Never create a permanent second repository, mirror-push old refs, or force-push the contaminated checkout into the new repository.
4. After an approved replacement, verify a changed repository ID; one main branch; no tags, PR refs, old commits, Actions caches/artifacts/logs or old Releases; expected initial source root; disabled production signing and read-only ordinary CI. Query historical SHAs/PR routes and unauthenticated visibility independently. Stop on unexpected reachability. Reconnect using a fresh clean checkout; keep old objects only in encrypted offline recovery.
5. Keep the new repository Private while running fresh exact-commit CI and unsigned builds/tests. Disable the manual release workflow by its new path-derived ID and verify read-only workflow defaults, zero repository/environment production secrets, zero Release assets, frozen update metadata and an empty media catalog. Production environments, signing keys and downloadable APKs are unnecessary for a source-only launch and must not be provisioned in this operation.

Rewriting main alone leaves PR refs, cached views and other retained objects. [GitHub's sensitive-data guidance](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository) explains those limits and the support route. Same-name recreation reduces the new repository's reachable surface; it does not prove erasure from GitHub backups, the restoration window, forks or external clones. Deleted repositories can remain [restorable](https://docs.github.com/en/repositories/creating-and-managing-repositories/restoring-a-deleted-repository). Keep all externally copied signing material classified as compromised. Never claim revocation from history replacement.

## Controlled Public transition on GitHub Free

The current private repository returns 403 for branch protection/rulesets under its plan. This is a deployment-order constraint, not permission to expose contaminated history. After the independent offline recovery check and owner-confirmed same-name Private replacement, prepare the ruleset requests and verify exact-commit CI before requesting the separate Public authorization.

In that explicitly authorized transition, change only the clean new repository to Public, then immediately apply and read back active rulesets with no bypass actors: main requires the successful `verify` check from GitHub Actions, an independent review with stale-review dismissal and last-push approval, conversation resolution and linear history; forced pushes and branch deletion are blocked. A second branch ruleset targets all branches except main and restricts their creation where supported. Contributor PRs originate from forks; do not create an official development branch.

Immediately enable/read back private vulnerability reporting, secret scanning and push protection where available. Verify from authenticated API and anonymous access: the new repository ID and Public visibility, sole/default main, exact source commit/tree, Apache-2.0 LICENSE and notices, effective branch rules, empty/frozen metadata, disabled production workflow, zero production credentials, zero Release/Actions APK assets and successful exact-SHA CI. If required rules or checks fail, stop the launch and return the new repository to Private for containment; do not call the launch complete or enable releases. Returning to Private does not erase an already public copy.

No production APK or immutable Release is required for this source-only launch. Before a later production release, separately approve key custody, trust/bootstrap design, production integration, platform/device acceptance, protected release controls and immutable Release settings. Keep the old-client bridge unchanged until trusted migration and remaining-client impact are proven and approved; its confirmed deletion is the final architecture-consolidation step.
