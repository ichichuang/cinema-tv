# 受损签名身份的迁移评审材料

状态：待维护者审阅与逐设备授权；本轮未生成替换生产密钥、未签署迁移包、未连接电视。正常构建和分发保持冻结。包名、UID、已安装数据、来源配置、设置与播放进度必须保留。

## 已核对的官方与工具边界

Android 的 [v3 文档](https://source.android.com/docs/security/features/apksigning/v3)说明 API 28 起支持签名轮换，同时明确提醒 Android 12 及以前的兼容性风险。[v3.1 文档](https://source.android.com/docs/security/features/apksigning/v3-1)与 [apksigner 文档](https://developer.android.com/tools/apksigner)说明默认轮换针对 API 33+；默认产物在 API 30 上仍可能使用旧签名身份。不能把“有 lineage”当作 Android 11 已迁移。

本轮读取了现有 Build Tools 36.0.0 的 `apksigner sign --help`、`rotate --help` 和版本输出。工具帮助确认：针对旧平台的轮换需要明确审查 `--rotation-min-sdk-version 28`；`--set-installed-data` 关系到原位保留数据；`--set-rollback true` 会让旧签名重新取得控制权，不能作为故障绕行。这里只核对帮助行为，没有签名实验或安装证据。

API 24–27 不支持 v3 轮换。在“原包名、保留数据、替换受损身份”三个约束下，没有已经验证可通用实施的升级方案；需单独决定旧设备支持策略，不能静默抬高 minSdk 或以换包/卸载解决。

## 独立信任引导

拥有旧私钥的攻击者也能为自己的替换公钥制作 lineage。因此，仅根植于受损旧证书的链不证明新身份属于合法维护者。需要维护者在现有仓库、旧签名与更新镜像之外的已验证渠道，建立替换证书 SHA-256、迁移 APK SHA-256 和迁移声明的独立信任；这些公开校验值要由设备操作者通过该渠道核对，不能从候选 APK 自报历史中取得信任。

替换私钥及独立元数据签名私钥只能由维护者在安全存储内生成并保管。选择什么渠道/信任根、如何确认维护者身份、如何安全备份与恢复，都尚待维护者明确；当前代码没有塞入临时密钥或接受任意证书。

历史已安装 updater 可能只比较旧证书；较新的完整集合比较同样会拒绝当前 signer 已变化的包。系统安装器接受轮换，不代表旧应用自身会下载/放行它。拟议的首次引导应在设备明确授权后，由操作者独立校验迁移产物并直接调用正常系统安装路线；如采用 ADB，只对明确指定的设备执行正常保留数据安装。不能绕过系统验签、授予旧钥匙回滚权、卸载或清数据。首次引导之后，再验证新应用的更新路径。

## 元数据和 APK 必须共同认证

兼容模式仍读取现有清单字段；可选 `sha256` 校验字节完整性，未签名清单里的摘要不提供独立发布者认证。本轮仅为更新专用客户端禁止 HTTPS 跨协议重定向，保留既有 HTTP 清单/下载地址兼容及媒体 HTTP 行为；HTTP 更新仍有篡改风险。

待审的新协议应签署明确的原始 payload 字节，覆盖包名、单调版本/发布序号、大小、APK SHA-256、允许的完整当前 signer 集、平台范围及有效期。由独立引导安装的客户端固定元数据公钥，并把最高已接受序号持久化；先验证签名、适用平台与重放条件，再下载并验证 APK。镜像地址不能更换信任根，不能在认证失败时回落到未签名旧协议。序列化规范、离线/时钟失败行为、密钥恢复及轮换策略需一起审阅，再替代现有兼容路线。

## 设备验收记录要求

1. 操作者明确设备和操作范围；记录真实 SDK、安装版本、当前证书及 UID。设置和进度仅在设备侧核对，报告不得含私有来源地址。
2. 从独立渠道确认迁移产物与新证书；核对实际签名的 SDK 范围、lineage 及旧 signer 能力。实验和产物隔离于普通构建及发布。
3. 在正常系统验签开启的情况下原位升级。前后包名、UID、设置、来源及进度一致，正常启动、声音和播放可用。
4. 通过迁移后的应用再完成一次合法后续更新，验证它自己的校验与系统安装器均通过；篡改包、无/错 signer、错包名、错版本、重放/降级均拒绝。
5. 独立验证旧密钥单独签署的候选被拒绝，不能只观察新包能安装。失败时保留证据，不能卸载、清数据或降低验证。

全部实际结果尚空缺。新代码的 JVM 单元测试不是 Android 固件的签名迁移实验，当前安全事件不能据此关闭。
